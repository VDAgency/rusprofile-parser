## 1. Контекст

Парсер Rusprofile — главный источник данных по ИНН/ОГРН для проекта.
До 2026-05-08 он стабильно собирал ~1000 компаний с фильтрами по
ОКВЭД, региону, выручке и т.п. После «тихого» обновления вёрстки
Rusprofile парсер начал возвращать пустой результат: форма поиска не
отрисовывается за установленный таймаут, JSON-ответ не приходит.

Параллельно в проект уже добавлены:
- БД с дедупом по теме (Tenant → Theme → ParseRun → RunCompany → Company);
- Mini App с автодополнением ОКВЭД и пресетами;
- HTTP API (история, repush, Excel в чат);
- Парсер Яндекс.Карт с итеративным добором до `max_new`.

Все эти компоненты завязаны на ту же сервисную обвязку
(`src/services/parse_service.py:run_rusprofile`), которая ожидает,
что внутренний парсер умеет:
- принимать `SearchFilters`;
- принимать предикат `is_new_predicate(company)`;
- принимать `max_new` и сам останавливаться при наборе;
- возвращать список `Company` с полями `name, inn, ogrn, region,
  address, okved, revenue, profit, phone, email, site, status,
  detail_href, parse_date`.

Сохраняем этот контракт. Меняем только то, что внутри —
работу с конкретным DOM-ом и сетевыми запросами Rusprofile.

## 2. Что есть сейчас (старая реализация)

### 2.1 Файлы

| Файл | Что делает | Статус |
|------|-----------|--------|
| `src/rusprofile/auth.py` | Двухэтапный логин на Rusprofile через Playwright (email → пароль), кеш cookies в `config/cookies.json`. | **Работает.** Логин проходит, сессия активна. |
| `src/rusprofile/filters.py` | `SearchFilters` + `filters_to_body()` — формирует body для POST `/ajax_auth.php?action=search_advanced`. | **Логика фильтров верна**, но ключ `body` мог измениться у нового endpoint-а. Структура SearchFilters остаётся. |
| `src/rusprofile/parser.py` | Открывает `/search-advanced`, перехватывает POST к `ajax_auth.php` через `page.route()`, подменяет body, читает JSON-ответ. | **Сломан.** Селекторы и URL устарели. |
| `src/services/parse_service.py:run_rusprofile` | Сервис-обёртка: tenant, theme, run, dedup, max_new, Sheets. | **Работает**, парсер вызывается правильно — переписывать не надо. |

### 2.2 Старая «механика» (для понимания)

1. `_goto(page, "/search-advanced")` — открыть форму расширенного поиска.
2. `wait_for_selector("#state-1")` — ждать, пока Vue смонтирует форму.
3. `page.route("**/ajax_auth.php*", handle_route)` — перехватчик для подмены body.
4. `page.evaluate(_SUBMIT_JS)` — нажать submit формы (`#filter-form`).
5. Получить JSON-ответ через `page.on("response")`.
6. JSON содержит `result[]` с полями `name, inn, ogrn, region, address, link, okved_descr, finance_revenue, inactive`.
7. Для пагинации — обновить `body["page"]` и повторить goto+submit.

### 2.3 Что Rusprofile сломал (по diag)

В `logs/diag/no_form_attempt*.html` (1.3 МБ HTML каждый) сохранены
полная страница после моего goto и скриншот. Найдено:

- **`id="state-1"` отсутствует** в HTML.
- Появился **`id="additional-search-state"`** — видимо, новый блок
  «Статус» в форме.
- В HTML страницы **нет упоминаний `ajax_auth.php`** —
  значит submit ушёл на другой endpoint (или передаётся через
  серверный рендеринг / новый API).
- Форма с `id="filter-form"` есть на странице (по grep видно).
- В скриншоте видно: на `/search-advanced` сразу отрендерилась
  страница с **готовым списком компаний** справа (`ООО Эскортер`,
  `АО Тагерс`, `FTPS`...) — то есть SSR/частичный SSR с дефолтным
  выводом, а не пустая форма.

Вывод: Rusprofile перешёл на другую модель работы с поиском.
Возможные варианты:
- Новый JSON-endpoint (`/api/...`) с тем же контрактом.
- SSR + AJAX по более простому GET-URL'у (как раньше было `/search`).
- HTMX/Hotwire-style (фрагменты HTML вместо JSON).

Точно — нужна разведка нового сетевого трафика.

### 2.4 Что в репозитории есть для разведки

## 3. Цель

Восстановить работоспособность парсера Rusprofile с тем же
интерфейсом для `parse_service.run_rusprofile`:

```python
async def parse_search_results(
    context: BrowserContext,
    filters: SearchFilters,
    progress_callback=None,
    is_new_predicate=None,
    max_new: Optional[int] = None,
) -> list[Company]:
    ...
```

Парсер должен:
- открывать новую вёрстку `/search-advanced` (или другой URL, если
  изменился);
- подавать фильтры (ОКВЭД, регион, статус, ОКОПФ, МСП, выручка,
  прибыль, контакты, бухотчётность);
- собирать карточки с полями name, inn, ogrn, region, address, okved,
  revenue, status, link;
- через `enrich_company_details` дополнительно собирать phone, email,
  site, profit;
- останавливаться по `max_new` при наборе нужного числа новых;
- работать с пагинацией.

## 4. Задачи (этапы)

### Этап 1. Разведка (2–4 часа)

Цель — точно понять, как работает новая выдача.

1. **Прогнать вручную через Playwright headed:**
   ```bash
   python scripts/diag_filters_final.py
   # или новый скрипт diag_new_search.py
   ```
   с включённым `headless=False`. Открыть DevTools, посмотреть:
   - какие XHR/fetch уходят при сабмите формы;
   - URL, метод, headers, body;
   - формат ответа (JSON / HTML / SSE);
   - есть ли пагинация — через POST-параметр или отдельный URL.

2. **Зафиксировать в новом diag-скрипте**
   `scripts/diag_new_search.py` точную «механику» — клик по
   submit, ожидание ответа, разбор. Сохранять `requests.har` для
   будущей сверки.

3. **Сверить body фильтров.** Возможно, формат body не изменился
   (Rusprofile часто оставляет совместимость) — тогда `filters.py`
   менять не нужно. Если изменился — описать новый контракт.

4. **Найти новый JSON-эндпойнт ИЛИ выяснить, что выдача через HTML.**
   Если HTML — будем парсить через BeautifulSoup из тела ответа
   или из DOM страницы.

5. **Зафиксировать пагинацию.** Как переходить на следующую страницу
   результатов: POST `page=2` / GET `?page=2` / прокрутка / кнопка.

**Артефакт этапа:** `docs/diag_rusprofile_new.md` — короткий отчёт
с примерами URL, тела запроса/ответа, скрин нужных селекторов.
Можно уточнить ТЗ перед этапом 2.

### Этап 2. Адаптировать `parser.py` (1 день)

1. Обновить `_fetch_page_json` (или переименовать в
   `_fetch_page_results`):
   - правильный селектор «форма готова» вместо `#state-1`;
   - правильный URL-фильтр в `page.route()` для перехвата запроса;
   - корректное поведение для нового метода (POST/GET) и формата
     (JSON/HTML).

2. Обновить `_company_from_json` или добавить
   `_company_from_html_card` — в зависимости от формата ответа.
   Сохранить контракт по полям.

3. Сохранить `is_new_predicate` и `max_new` — они уже встроены и
   тестируются `parse_service.run_rusprofile`.

4. Сохранить `enrich_company_details` — она работает с детальной
   страницей `/id/N`, которая, скорее всего, **не менялась**.
   Если поменялась — отдельный подэтап.

### Этап 3. Тесты (0.5 дня)

1. Юнит-тест на `_company_from_json` (или новый эквивалент) с
   фикстурой ответа Rusprofile (положить в
   `tests/fixtures/rusprofile_search_response.{json,html}`).
2. Регрессионный тест на `filters_to_body` — убедиться, что

3. (опц.) Сквозной тест с моком `page.route()` — проверить, что
   парсер корректно обрабатывает 1+ страницу.

### Этап 4. Деплой и боевая проверка (0.5 дня)

1. Локально — `pytest tests/`, прогнать `python scripts/diag_new_search.py`.
2. Push в main, на сервере `git pull`, перезапустить бот.
3. В Mini App запустить парсинг с фильтром «Самарская область,
   ОКВЭД 46.49.3, лимит 10 новых».
4. Проверить: компании пришли в Sheets, метрики run корректные,
   `links_total = links_new = total_new`.
5. Проверить, что Яндекс.Карты по-прежнему работают (smoke).

**Итого:** ~2–3 рабочих дня от начала разведки до прода.

## 7. Риски

* **Rusprofile может закрыть JSON-API или повысить требования
  безопасности** (CSRF в headers, rate-limit). Тогда придётся
  парсить HTML, что медленнее.
* **Антибот.** Скорее всего наш Playwright-стек проходит, но если
  Rusprofile добавил Cloudflare или подобное — потребуется
  настройка прокси/имитации браузера.
* **Изменение контракта `filters.py`.** Если новый endpoint ждёт
  другие имена параметров — придётся переписать; UI не менять,
  потому что Mini App шлёт всё в наш `SearchFilters`.
